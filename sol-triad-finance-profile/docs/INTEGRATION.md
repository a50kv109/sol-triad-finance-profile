# Контракт интеграции с учётными системами и ядром (Integration Contract)

**Статус:** Архитектурное руководство по интеграции

---

## 1. Концепция включения в корпоративный ландшафт

SOL-Triad Finance Profile не заменяет существующие учётные системы (1С, ERP, банковские АБС), а функционирует как независимый контур структурной верификации и предпроверочного анализа.

### Полная схема взаимодействия:
```
[ Бухгалтерская система (напр., 1С:Предприятие / ERP) ]
                  │
                  ▼ (1. Экспорт проводки/платежного поручения через официальный API)
[ Специализированный Адаптер Системы (Custom Host Adapter) ]
                  │
                  ▼ (2. Формирование TaskRequest и HostPolicy)
[ SOL-Triad Finance Profile (Адаптируемый каркас) ]
                  │
                  ▼ (3. Трансляция в канонические примитивы S, C, D)
[ SOL-Triad Core (Математическое ядро верификации) ]
                  │
                  ▼ (4. Детерминированный вердикт PASS / REVIEW / FAIL)
[ Внешний Исполнительный Контроллер (Host Execution Controller) ]
                  │
                  ▼ (5. Возврат статуса проверки и рекомендаций)
[ Отражение в бухгалтерской системе (проведение / отклонение операции) ]
```

## 2. Позиционирование по отношению к учётным программам (1С и др.)

1. **Отсутствие коробочных сертифицированных коннекторов:**  
   В репозитории **не содержится готовых сертифицированных модулей расширения или обработок для 1С или иных ERP-систем**. Любые упоминания систем приводятся исключительно в качестве архитектурных примеров целевой интеграции.
2. **Разработка адаптера силами интегратора:**  
   Организация-интегратор разрабатывает внешний коннектор (на официальном языке и через официальные интерфейсы целевой системы: REST API, OData, Web-сервисы, очереди сообщений).
3. **Отдельная проверка:**  
   Интеграция с конкретной учётной базой должна отдельно тестироваться на тестовых копиях баз данных с привлечением штатных финансовых специалистов и бухгалтеров.

## 3. Роль базового каркаса `FinanceFxAdapter`

Реализованный в коде `FinanceFxAdapter` демонстрирует базовый эталон трансляции финансовых понятий в примитивы SOL:

1. **Приём входных данных:** Адаптер принимает `TaskRequest` (недоверенный запрос на операцию) и `HostPolicy` (доверенную политику хоста с лимитами и системным временем).
2. **Предварительная валидация до вызова ядра:**
   - Сверка счёта списания: `task_req.source_account_id == policy.authorized_account_id`.
   - Проверка санкционированного домена потерь: `task_req.requested_loss_domain == policy.authorized_loss_domain`.
   - Проверка математической корректности сумм и курсов.
3. **Трансляция в каноническую триаду:**
   - **SOURCE ($S$):** Ссылка на котировку или нормативное основание из доверенного реестра хоста (`evidence_quote_id`), статус `FACT`, время и хэш.
   - **CONSTRAINT ($C$):** Защитные границы (минимальный баланс $B_{\min} = 0.0$ для предотвращения несанкционированного овердрафта, предельная сумма операции).
   - **DISSIPATE ($D$):** Вектор воздействия на счета (`state_delta = {source_account: -amount, target_account: +amount_target}`).
   - **INITIAL STATE ($S_0$):** Актуальные подтверждённые балансы из `HostPolicy.current_balance`.
4. **Вызов канонического ядра:** Вызов `SolTriadCoreKernel.evaluate(...)` с системным временем хоста и реестром.
5. **Формирование результата:** Возврат `FxPaymentResult` с вердиктом, кодами диагностики и гарантией `execution_permitted = False`.

---

## 4. Изоляция адаптаций для разных организаций

- Правила бухгалтерского учёта и форматы экспорта данных для компании «А» не должны вноситься в код базового профиля.
- Для каждой новой интеграции создаётся обособленный модуль адаптера, наследующий или вызывающий интерфейс профиля.
- Это предотвращает регрессии и взаимное влияние разнородных учётных политик.
