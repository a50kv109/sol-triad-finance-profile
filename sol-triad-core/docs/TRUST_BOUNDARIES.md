# Границы доверия и модель угроз SOL-Triad Core

**Статус:** Нормативное руководство по безопасности (Trust Boundaries & Threat Model)

---

## 1. Архитектурные границы доверия

При интеграции SOL-Triad Core с внешними агентами и системами действуют строгие границы доверия:

```
[ НЕПРОВЕРЕННАЯ ЗОНА ]                    [ ДОВЕРЕННАЯ ЗОНА ХОСТА ]
  (Agent / Planner)                       (Host Runtime / Controller)
         │                                             │
         │ Недоверенный JSON / Запрос                  │ Доверенное время: time.time()
         │ { action, delta, evidence_id }              │ Доверенный реестр: host_registry
         ▼                                             │ Доверенная политика: host_policy
   ┌───────────┐                                       │
   │  АДАПТЕР  │◄──────────────────────────────────────┘
   │ (Шлюз)    │ (Отсекает инъекции, валидирует типы, собирает контекст)
   └─────┬─────┘
         │
         │ Канонический вызов evaluate(S, C, D, S0, t_eval, registry)
         ▼
   ┌───────────┐
   │   ЯДРО    │ (Детерминированная математическая верификация)
   │ SOL-Triad │ ──► Отчёт: PASS / REVIEW / FAIL, execution_permitted = False
   └─────┬─────┘
         │
         │ Вердикт и симулированные значения
         ▼
   ┌───────────────────────┐
   │ ИСПОЛНИТЕЛЬНЫЙ ШЛЮЗ   │ (Execution Controller хоста)
   │ (Host Execution Gate) │ Решает: совершать ли физическое действие (платёж/команду)
   └───────────────────────┘
```

## 2. Анализ 5 критических векторов атак (Threat Vectors)

### Вектор 1: Инъекция системного времени хоста (`evaluation_time_sec`)
- **Угроза:** Агент пытается передать собственное устаревшее или будущее время в теле запроса, чтобы скрыть факт устаревания котировки или телеметрии.
- **Защита ядра:** Ядро принимает время оценки строго как отдельный скалярный параметр вызова `evaluation_time_sec: float`, предоставляемый хостом. Адаптер JSON (`SolTriadJsonGateway`) **безусловно отклоняет** любой JSON-документ, содержащий ключ `"evaluation_time"`, со статусом `STRUCTURAL_DEFECT` и вердиктом `FAIL`.
- **Защита в продуктовом адаптере (Finance FX):** Время берётся исключительно из доверенного объекта `HostPolicy.evaluation_time`.

### Вектор 2: Инъекция реестра свидетельств (`evidence_records`)
- **Угроза:** Агент передаёт внутри своего запроса «фиктивную запись доказательства» (self-minted evidence) и заставляет ядро поверить в неё.
- **Защита ядра:** Реестр свидетельств `registry` передаётся исключительно хостом при вызове ядра. Чтение `evidence_records` из JSON полностью устранено. Наличие ключа `"evidence_records"` в JSON-запросе приводит к немедленному отказу `FAIL (STRUCTURAL_DEFECT)`.

### Вектор 3: Обход проверки через флаги доверия (Trust Flags Anti-Pattern)
- **Угроза:** Наличие в сигнатуре адаптера параметра вида `trusted_host_context: bool = False`, который недоверенный вызывающий код может передать со значением `True`.
- **Защита ядра:** В кодовой базе ядра и его адаптеров **полностью отсутствуют булевы флаги доверия**. Ни один метод не принимает `trusted_host_context`, `is_trusted` или аналогичные флаги. Граница доверия задаётся архитектурным разделением каналов: недоверенные данные передаются в теле полезной нагрузки, а доверенный контекст — через отдельные параметры API хоста.

### Вектор 4: Конфликт и подмена доменов потерь (`Loss Domain Spoofing`)
- **Угроза:** Агент запрашивает операцию в домене `unlimited_drain`, в то время как хост санкционировал только `funds_transfer`.
- **Защита ядра и адаптера:**
  1. В адаптере: поле агента `task_req.requested_loss_domain` проверяется против `policy.authorized_loss_domain`. При несовпадении адаптер отвергает запрос до ядра (`UNAUTHORIZED_LOSS_DOMAIN`).
  2. В ядре: аксиома SD-1 ($P_{SD}$) строго проверяет $D.\text{loss\_domain} \subseteq S.\text{granted\_loss_domains}$. Подмена любого элемента вызывает отказ `SCOPE_EXCEEDED_LOSS`.

### Вектор 5: Тавтологическая проверка (Сравнение значения с самим собой)
- **Угроза:** Адаптер берёт значение, присланное агентом (например, курс котировки или домен), помещает его и в проверяемый объект, и в эталонный объект, создавая ложное совпадение.
- **Защита:** Эталонные значения (котировка, остаток на счёте, лимит) поступают исключительно из `HostPolicy` и `host_registry`. Агентские данные никогда не используются в качестве эталона для самих себя.

## 3. Матрица разделения ответственности

| Ответственность | Компонент | Механизм контроля |
|---|---|---|
| Проверка валидности JSON и отсечение запрещённых полей хоста | Адаптер (`SolTriadJsonGateway`) | Безусловный отказ при обнаружении `evaluation_time` или `evidence_records` |
| Проверка полномочий и физических законов | Ядро (`SolTriadCoreKernel`) | Детерминированные аксиомы $P_{SC}, P_{SD}, P_{CD}$ |
| Поставка доверенных котировок, времени и лимитов | Хост-окружение | Подписание/регистрация в `EvidenceRegistry` и создание `HostPolicy` |
| Разрешение на выполнение реального действия (платежа, запуска двигателя) | Исполнительный Контроллер (Execution Controller) | Проверка вердикта ядра (`report.verdict == PASS`), проверка подписи отчёта и локальных прав |
