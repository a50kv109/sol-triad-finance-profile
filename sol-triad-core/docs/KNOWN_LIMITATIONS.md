# Известные ограничения и вопросы, требующие согласования

**Статус:** Реестр открытых архитектурных вопросов (Known Limitations & Discussion Points)

---

## 1. Известные ограничения текущей реализации

1. **Криптографическое хэширование полезной нагрузки:**
   - *Фактическое состояние:* Ядро проверяет строгое строковое равенство $S.\text{payload\_hash} == R.\text{payload\_hash}$. Вычисление криптографического дайджеста (например, SHA-256) из произвольного бинарного или JSON-тела выполняется внешним поставщиком свидетельств при регистрации в `EvidenceRegistry`, а не ядром на лету.
   - *Обоснование:* Каноническое ядро не должно зависеть от форматов сериализации полезной нагрузки (protobuf, msgpack, json-canonicalization-scheme).

2. **Модель реестра свидетельств:**
   - *Фактическое состояние:* В эталонной реализации предоставлен потокобезопасный `InMemoryEvidenceRegistry`. В реальном промышленном контуре хост должен реализовать интерфейс `EvidenceRegistryOracle` поверх распределённой БД, PKI или HSM.

3. **Линейная физическая конверсия:**
   - *Фактическое состояние:* Реестр размерностей `UnitRegistry` поддерживает стандартные линейные масштабы (СИ) и аффинное смещение для температуры (Цельсий $\leftrightarrow$ Кельвин). Нелинейные шкалы (логарифмические, децибелы) не поддерживаются.

4. **Отсутствие прямого исполнения:**
   - *Фактическое состояние:* Ядро и адаптер возвращают математический вердикт и симулированное терминальное состояние. Физическое исполнение (диспатчеризация команд, банковский клиринг) возложено на внешний `ExecutionController`.

---

## 2. Вопросы, требующие согласования с пользователем

1. **Унификация именования вердиктов:**
   В ранних концептуальных черновиках SOL встречались термины `COHERENT / INCOHERENT / AMBIGUOUS`. В эталонной кодовой базе и тестах v0.4.0+ зафиксированы `PASS / FAIL / REVIEW`. Рекомендуется окончательно закрепить `PASS / REVIEW / FAIL` как канонический стандарт.

2. **Стандартизация формата канонического хэширования JSON:**
   Для прямой верификации JSON-хэшей в адаптере требуется утвердить стандарт канонизации (например, RFC 8785 JSON Canonicalization Scheme — JCS). Пока сверяются готовые маркеры хэшей.

3. **Многодоменные профили:**
   В качестве первого продуктового адаптера выступает `FinanceFxAdapter` (валютный профиль). Требуется согласовать следующий целевой специализированный модуль (например, профиль управления промышленными контроллерами / робототехникой).
