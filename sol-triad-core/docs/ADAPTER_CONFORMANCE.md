# Руководство по разработке конформных адаптеров (Adapter Conformance Guide)

**Статус:** Нормативное руководство для интеграторов

---

## 1. Назначение адаптера

Адаптер — это изолированный компонент, расположенный между внешним продуктом (банковский шлюз, диспетчер робототехники, планировщик LLM-агента) и каноническим ядром SOL-Triad Core.

### 5 обязательных шагов конформного адаптера:
1. **Приём входных данных продукта:** Адаптер принимает структуры данных в идиоматичном для продукта формате (REST JSON, gRPC, структуры языка).
2. **Валидация происхождения и отсечение инъекций:** Адаптер проверяет границы доверия:
   - Не позволяет внешнему запросу перезаписывать доверенные поля хоста (время, политику, реестр).
   - Проверяет синтаксическую корректность и типы.
3. **Двусторонняя трансляция в каноническую модель:** Адаптер переводит данные продукта в примитивы $S, C, D, S_0$.
4. **Вызов детерминированного ядра:** Передаёт канонические сущности вместе с доверенными аргументами `evaluation_time_sec` и `registry`.
5. **Трансляция результата продукта:** Преобразует `EvaluationReport` в ответ принимающей системы, **не искажая смысл вердикта** и гарантируя сохранение `execution_permitted = False`.

---

## 2. Антипаттерны при создании адаптеров

1. **Встраивание продуктовой логики в ядро:** Нельзя модифицировать канонические классы ядра ради удобства одного продукта.
2. **Самоприсвоение доверия (Trust Flags):** Адаптер не должен предоставлять вызывающему коду аргументы вроде `trusted=True`, `bypass_verification=True`.
3. **Тавтологическая валидация:** Адаптер не должен брать данные из заявки агента и использовать их одновременно как заявку и как эталон.
4. **Прямое исполнение действий:** Адаптер ядра не должен самостоятельно выполнять операции (списывать средства, подавать питание). Исполнение должно оставаться за отдельным контроллером хоста.
